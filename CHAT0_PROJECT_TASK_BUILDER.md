# Extranjeria Notifier — тест-план проверки доставки и матчинга

## PLAN (что проверяем)
Цель: доказуемо подтвердить 4 вещи:
1. Уведомления действительно доставляются в Telegram.
2. Логика «кому отправлять / кому не отправлять» работает корректно.
3. Для типовых кейсов есть понятная причина недоставки.
4. Нет «тихих» провалов из-за конфигурации/ограничений.

Ограничения: без изменения алгоритма и без патчей в коде — только проверка существующим UI и командами `/testnotify`, `/auditnotify`, `/start`, переключателями выбора провинции/офиса/сервиса.

---

## BUILD (пошаговый таск-лист, 14 сценариев)

> Формат фиксации каждого сценария: **Ожидаемое** / **Фактическое** / **Статус (PASS/FAIL)** / **Причина (если FAIL)**.

### 1) Smoke доставки (базовый)
- Действия: фейк-юзер A → `/start` → выбрать `province+office+service` → включить уведомления (ON) → `/testnotify`.
- Ожидаемое: сообщение пришло в чат A.

### 2) Проверка HTML и кнопок
- Действия: на сообщении из шага 1 проверить формат текста (HTML-рендер) и inline-кнопки.
- Ожидаемое: виден HTML-формат; есть кнопки **«Відкрити сайт»** и **«Меню»**.

### 3) Три разные конфигурации выбора
- Действия: для того же юзера A по очереди выставить 3 разные комбинации `prov/office/service` и каждый раз запускать `/testnotify`.
- Ожидаемое: все 3 тестовых уведомления доставлены.

### 4) OFF-состояние (enabled=False)
- Действия: отключить уведомления у юзера B (или не включать вовсе), админ запускает `/auditnotify`.
- Ожидаемое: в отчёте есть кейсы с причиной `disabled` и статусом не-send.

### 5) Province mismatch
- Действия: у тестового юзера выставить провинцию, отличающуюся от «события», выполнить `/auditnotify`.
- Ожидаемое: причина `province_mismatch`.

### 6) Service mismatch
- Действия: выставить сервис, не совпадающий с «событием», выполнить `/auditnotify`.
- Ожидаемое: причина `service_mismatch`.

### 7) Office mismatch (другой офис)
- Действия: та же провинция и сервис, но офис другой; выполнить `/auditnotify`.
- Ожидаемое: причина `office_mismatch`.

### 8) Office = any
- Действия: если в данных возможно выставить `office_id=any`, выполнить `/auditnotify`.
- Ожидаемое: классификация как `office_mismatch`.

### 9) Office пустой / None
- Действия: если в данных возможно пустое значение офиса, выполнить `/auditnotify`.
- Ожидаемое: `office_mismatch`; пользователь не попадает в релевантную «группу дня».

### 10) Cooldown: 5 минут
- Действия: в синтетических кейсах `/auditnotify` проверить пользователя с `last_alert_min = now-5`.
- Ожидаемое: причина `cooldown_lt_25m`.

### 11) Граница cooldown 24 vs 25
- Действия: в `/auditnotify` сравнить кейсы `now-24` и `now-25`.
- Ожидаемое: `24` блокируется (`cooldown_lt_25m`), `25` допускается (`send`).

### 12) Random skip 15% в реальной рассылке
- Действия: зафиксировать при наблюдении циклов `notifier_loop`, что часть матчей может не получить уведомление.
- Ожидаемое: отсутствие части доставок допускается как штатное поведение (`apply_random_skip=True`).

### 13) Выходные (weekend gate)
- Действия: проверить поведение в субботу/воскресенье (или в тестовом окне с соответствующим днём).
- Ожидаемое: фоновая рассылка не отправляет уведомления.

### 14) Рестарт во время рассылки
- Действия: зафиксировать сценарий «событие уже помечено fired, но процесс рестартнул до завершения отправки».
- Ожидаемое: после рестарта событие не дублируется повторной отправкой.

## REVIEW / VERIFY (критерии приёмки)

### Обязательные критерии DoD
- `/testnotify` доставляет уведомления минимум для 3 разных комбинаций `prov/office/service`.
- `/auditnotify` доступен администратору и показывает 20 синтетических кейсов.
- В `/auditnotify` при валидном выборе админа есть минимум 3 кейса со статусом `send`.
- Для ключевых негативных случаев (disabled/mismatch/cooldown) видны явные причины недоставки.
- Подтверждены HTML-формат и кнопки «Відкрити сайт» + «Меню».
- Подтверждено, что по выходным фоновая рассылка не уходит.

### Лог фиксации результатов (рекомендуемый шаблон)
| Сценарий | Ожидание | Факт | Статус | Комментарий |
|---|---|---|---|---|
| S1 Smoke delivery | Дошло | ... | PASS/FAIL | ... |
| S2 HTML+buttons | Есть HTML+2 кнопки | ... | PASS/FAIL | ... |
| ... | ... | ... | ... | ... |

### Диагностика «почему не пришло» (быстрая шпаргалка)
- Не админ → `/auditnotify` недоступен (проверить `ADMIN_IDS`).
- У пользователя OFF → ожидаемо `disabled`.
- Несовпадение prov/service/office → ожидаемо `*_mismatch`.
- Недавняя отправка → `cooldown_lt_25m`.
- В реальном цикле может сработать рандомный skip 15%.
- В выходные фоновая рассылка отключена.
