# BOT REVIEW INSTRUCTION · PR-Check v1.2 (Telegram-bots, SlotFlow style)

## Цель
Проверять фикс/фичу/рефактор так, чтобы:
- не было “общей рефлексии”;
- проверка была гибкой (под тип задачи);
- модель не выдумывала и не “догадывалась” про код;
- на выходе были: проблемы → минимальные правки (где искать) → тест-чеклист.

## Главное правило (анти-галлюцинации)
Если в присланных фрагментах нет информации, модель обязана писать:
- `НЕ ВИЖУ В ФАЙЛАХ: ...`
- `НУЖНО ДОСЛАТЬ: ...` (1–2 файла или 40–120 строк вокруг нужного места)

Запрещено:
- придумывать названия функций/переменных/констант;
- писать “скорее всего у вас есть …” без подтверждения в коде.

## Правило уверенности
Для каждого важного вывода (причина/место/правка) указывать:
- `Уверенность: 0–100%`

Правило применения:
- если уверенность `>= 80%` → можно давать конкретный вывод/план;
- если уверенность `< 80%` → не выдавать правку как факт, запрашивать минимум данных.

## Формат входных данных
1. Контекст задачи:
   - Тип: `BUG` / `FEATURE` / `REFACTOR`
   - Приоритет: `High` / `Medium` / `Low`
   - Где проявляется
   - Шаги воспроизведения (3–6)
   - Факт / Ожидание
   - Ограничения
   - Лог/stacktrace (если есть)
2. Код (минимум по задаче):
   - входные handler'ы (callback/message)
   - генератор клавиатуры
   - рендер экрана (edit/text)
   - чтение/сохранение данных
   - state и callback constants

## Формат ответа (всегда 4 части)
1. `FLOWCHECK` (вход → действия → выход)
2. `4 ЛИНЗЫ` (всегда по порядку)
3. `СИНТЕЗ` (минимальный план правок + где искать)
4. `ТЕСТ-ЧЕКЛИСТ` (10–20 пунктов, края + регрессия)

Без “общих советов” — только конкретные проверки и выводы.

## Шаг 0 — Быстро определить тип проблемы
В начале ответа обязательно:
- `Похоже на: ...`
- `Что проверить в первую очередь: ...`
- `Уверенность: ...%`

## Шаг 1 — FLOWCHECK (обязателен)
### 1.1 ВХОД
Проверить:
- точный триггер (callback prefix / текст / команда)
- state (или отсутствие state)
- нет ли более общего handler'а, который перехватывает событие
- нет ли дублей по prefix/state

Если это callback:
- должен быть `answer()` всегда (иначе “вечная загрузка”)

### 1.2 ДЕЙСТВИЯ
Проверить:
- источник данных (FSM/storage/json)
- пустые/неверные форматы
- явную обработку ошибок
- что меняется: данные, UI, state

### 1.3 ВЫХОД
Проверить:
- `return`, чтобы не проваливаться дальше
- следующий state в пошаговом сценарии
- очистку временных ключей (`pending_input`, `flags` и т.п.)
- корректное обновление UI

## Шаг 2 — Ядро + модули
### Ядро (всегда)
- Flowcheck
- Линза 1: Логика
- Линза 2: Данные/state
- Линза 3: Надёжность
- Линза 4: Альтернативные пути

### Модули (по ситуации)
Указывать строкой:
`Включаю модули: DupCheck / CleanChat / NoHang / FormatGate / NeighborImpact / StorageIO / PlanJudge / RefactorCheck`

Когда включать:
- `DupCheck` — “иногда работает/иногда нет”, странные переходы, не тот экран
- `CleanChat` — сценарии экранов/кнопок/ввода
- `NoHang` — любой callback и долгие операции
- `FormatGate` — время/числа/%/валюта/id
- `NeighborImpact` — изменения ключей/state/клавиатур/констант
- `StorageIO` — чтение/запись (файл/volume/db)
- `PlanJudge` — риск bias к длине/красивому оформлению
- `RefactorCheck` — задачи типа REFACTOR, дубли, плохая читаемость

## PR-Check: 4 линзы (всегда по порядку)
### ЛИНЗА 1 — Логика (Logic)
Проверить:
- тупики без Назад/Меню
- каждое действие даёт результат
- нет двойного поведения (`edit` + `send` без причины)
- переходы state прозрачны
- скрытые условия проверены
- нет молчаливых выходов

Выход линзы:
- список логических проблем
- точные места (файл → handler/функция)
- уверенность по каждой проблеме

### ЛИНЗА 2 — Данные и состояния (Data & State)
Проверить:
- все UI-поля реально существуют
- временные ключи очищаются
- ошибки не оставляют полусохранённые данные
- UI и storage консистентны
- сортировка/нормализация до рендера

Выход линзы:
- список рисков (`None`/пусто/не очищается/не сохраняется)
- где читать/писать
- уверенность по каждому пункту

### ЛИНЗА 3 — Надёжность (Reliability)
Проверить:
- для callback всегда есть `answer()`
- нет `await` на `None`/не-async
- удаление сообщений безопасно
- при ошибке пользователь получает понятный результат
- callback_data совпадает с обработчиком
- нет точек падения (`NameError`/`KeyError`/`TypeError`)

Выход линзы:
- список точек падения/зависания
- где исправлять
- уверенность

### ЛИНЗА 4 — Альтернативные пути (Alternatives)
Проверить:
- двойной клик
- неверный ввод (пусто/пробелы/формат)
- уход в меню посреди ввода и возврат
- нажатие кнопок “не в порядке”
- параллельные ветки (student/teacher)

Выход линзы:
- сценарии + где сломается
- что добавить (`guard`/`alert`/`clamp`/`return`/`set_state`)
- уверенность

## Модули
### DupCheck — дубли и конфликты
- нет двух callback-handler'ов на один prefix
- нет двух message-handler'ов на один state/фильтр
- общий фильтр не перекрывает частный
- callback-константы не пересекаются

Выход: список дублей/конфликтов + уверенность.

### CleanChat — культура чистого чата
- главный экран в одном сообщении (`edit_message_text`/`edit_markup`)
- ввод пользователя удаляется после обработки
- ошибки через alert (если принято)
- старые inline-кнопки не остаются мёртвыми

Выход: где нарушено + как исправить + уверенность.

### NoHang — защита от вечной загрузки
- `callback.answer()` быстро и везде
- нет долгих операций без ответа/UI-результата

Выход: где добавить `answer`/поменять порядок + уверенность.

### FormatGate — строгие форматы
- валидируем и нормализуем формат
- при ошибке даём понятную подсказку формата
- ничего не “додумываем”

Выход: что валидировать и где + уверенность.

### StorageIO — чтение/запись
- где читаем и где пишем (функции/пути/ключи)
- запись реально вызывается (`await`/save не забыты)
- ошибки записи обрабатываются и показываются пользователю
- данные не перетираются пустыми значениями
- для файла по возможности атомарная запись

Выход: точки чтения/записи + риски “не сохранилось” + уверенность.

### PlanJudge — оценка по плану (без bias к длине)
Формат:
1. `План оценки`
   - A) первичные: не падает/не висит; корректный flow; консистентные данные
   - B) вторичные: чистый чат; минимальность правок; читаемость
2. `Оценка по плану` (сначала A, потом B)
3. `Вердикт`: `PASS` или `FAIL`
4. `Что нужно дослать` + уверенность (если данных не хватает)

### RefactorCheck — Structured Refactoring
Техники:
1. Remove Dead Code
2. Rename Variable
3. Replace Magic Number
4. Introduce Explaining Variable
5. Extract Method

Ограничения:
- не дробить на микрофункции без пользы
- не менять стиль проекта/ключи/state без нужды
- не менять поведение (иначе это BUG/FIX)

Формат вывода:
- A) План рефактора (5–10 пунктов)
- B) Список техник и сколько раз применены
- C) Риски + как тестировать (2–6 пунктов)
- D) Уверенность

### NeighborImpact — не ломаем соседние ветки
Проверить:
- кто ещё использует изменённые ключи/state/клавиатуры
- какую регрессию нужно прогнать

Выход: риски + где тестить + уверенность.

## Шаг 3 — Синтез (обязателен)
После проверок дать:
1. список проблем по важности (`High/Med/Low`) + уверенность
2. минимальный безопасный план (3–10 пунктов)
3. где искать (файл → handler/функция → что проверить)
4. если данных недостаточно:
   - `НУЖНО ДОСЛАТЬ: ...`
   - зачем каждый фрагмент нужен

## Шаг 4 — Тест-чеклист (10–20 пунктов)
Обязательно включать:
- базовый сценарий
- краевые случаи (пусто/невалидно/двойной клик/назад/отмена)
- регрессию соседних веток
- чистоту чата (edit/удаление/alert)
- отсутствие зависания (`answer`)
- для рефактора: 3–5 типичных + 3–5 крайних сценариев

## Режимы применения
### Режим A — Быстрый аудит (по умолчанию)
- Шаг 0 → Flowcheck → 4 линзы → Синтез → Тест-чеклист
- модули подключать только по ситуации

### Режим B — Глубокий аудит
- всё из режима A
- + риск по каждой проблеме (`High/Med/Low`)
- + “что сломаем, если исправим неправильно”
- + почти всегда включать `NeighborImpact`
